## The highest-value unfinished thing

**Authoritative control semantics for OS 9's own panels — plan 018 slice
18, and its named successor "slice 19" (the CDEF route), which was
started and left half-landed.**

Everything else in this arc changes how well the product is *described*.
This one changes what the product can *do*.

The chain, derived:

- `GetControlKind` is Mac OS X only (Universal Interfaces
  `Controls.h:2310`); CarbonLib 1.6 does not export it. The resident
  already does the correct substitute
  (`GetControlData(…, kControlKindTag, …)` in
  `ext/src/now_semantic.c :: classify_member`).
- The Control Manager **declines** for `CNTL`-resource controls made by
  `GetNewControl` — which is every control in every OS 9 control panel.
  Measured: Date & Time 21/21 refused; Appearance 62 of 73 refused.
- So the authoritative answer *does not exist* for exactly the windows
  the product most needs it for. **Rendered but not usable** is the
  result, and it is the largest single instance of this arc's recurring
  split. Michelle named it directly: *"lists, scrollbars and tabs render
  now but they cant be used."*
- `018-cdef-classify` took the CDEF-resource-id route and got **71 of
  Appearance's 73 classified**, including the tab strip, the theme list
  and the scroll bar. That is real and it landed.
- **It stops one step short of usability, and the stopping point is
  visible in the product right now:** Memory's six radios and its check
  box come back CDEF 0 variant 0 → `pushButton`, and now draw as *bare
  labels*. The variant byte is not in `contrlDefProc`'s high byte on a
  32-bit-clean OS 9. The known route is `GetControlVariant`, which is a
  guest-side Toolbox call on a **foreign** `ControlHandle` — a design
  question against `resident-components.md`'s foreign-memory /
  foreign-execution division, and it needs a guest build and a machine.

Finishing this is what turns a picture of a control panel into a control
panel. It is also the item that funds both products at once: the native
file/proc server host-side Finder described in plan 019 inherits this
exact gap.

**Runner-up, for a different reason:** the drag vehicle
([slice 10](#slice-10--drag-as-an-act-primitive)). It is the only
capability in the arc that is fully built, has passing gates, and has
**never once been pointed at the thing it exists for**.

<a name="p3-is-a-spotlight"></a>
## The finding that changes the shape of this accounting

**P3 — the content plane — is not a plane. It is a per-window,
TTL-bounded spotlight.** From `claude/019-content-never-active`,
emulator-verified with a mutation control.

- P1, P2 and P4 echo `arm_request` unconditionally. **P3's bit is set in
  exactly one place** (`ext/src/now_content.c:1843`), and the only thing
  that claims it is `qdtrace start`.
- Measured: baseline walk arms **7**; `qdtrace start` arms **15**;
  `qdtrace stop` returns to **7**.
- **`tools/local-pair-capture.py` — the drive loop's own live
  instrument — never issues `qdtrace start`.** Verified here: zero
  occurrences of the string `qdtrace` in that file. So every `display`
  it captures is nil **by construction**, and every window it looks at
  hatches.

**What this voids, and — importantly — what it does not.** I checked the
blast radius rather than accepting the general form of the claim:

- **`tools/fidelity-sweep.py` DOES issue `qdtrace start`** (line 220,
  with a status floor at 217 and a `SKIPPED: qdtrace refused` path at
  225). So **Sweep A, Sweep B and round 5's LOOK are not voided by this**
  — they armed the plane, and the ones that could not say so.
- **What IS voided is every hatching observation taken through the drive
  loop's pair capture.** Those are not measurements of the product; they
  are measurements of an unarmed plane. Any conclusion of the form "this
  window's interior is unavailable," reached through
  `local-pair-capture.py`, must be **re-taken with `qdtrace start`
  before it is believed.**

I could not enumerate exactly which of the arc's hatching findings came
through which instrument, so **the honest statement is that an unknown
subset is artefactual and the boundary is knowable in one pass**: re-run
the affected targets through the sweep, which arms correctly. Until then
**no prior hatching row is settled**, and this document treats them all
as unconfirmed rather than deleting them.

### And it is the eighth instance of one pattern

**The instrument's normal mode of operation is the one condition under
which the defect cannot appear.** The instances in this arc alone:

1. The MCP transport bug survived because **every driver ever written
   closed stdin** — *"a pipeline that closes the pipe is a batch, not a
   client."*
2. Sweep A's stability score rendered a **settled capture twice**, so it
   could not see flicker, and would have reported "stable" either way.
3. `NOWMirrorContentCoverageTests` ran against a fixture with
   `controls = []` — the one input where the content defect is absent.
4. The bake receipt's `qemu-img check` inspects the container, never the
   HFS volume — *"a check adjacent to the question reads exactly like an
   answer to it."*
5. Every fidelity score is a whole-window similarity, so a **systematic**
   1-pixel offset degrades all of them slightly and names nothing.
6. The planes arm **as a result of** the first `scene.request`, so a
   first-on-connection capture returns every role `unknown` — the rig's
   normal opening move produces a perfect forgery of a real defect.
7. A process acquires an anchor slot **only while itself pumping events
   with the plane armed**, so a passive observer measures the anchor
   defect and calls it a render defect.
8. **P3 is armed only by `qdtrace start`, which the drive loop's own
   instrument never sends** — so its default mode guarantees the empty
   interior it then reports.

Eight instances, all in one arc, all costing real hours. **That is a
corpus finding, not a docs note.** It generalises past this project: an
instrument whose default configuration is the defect's blind spot will
read green forever, and no amount of care in reading its output will
recover the signal. The countermeasure that worked every time here was
the same one: **put the machine's own pixels beside the instrument's
answer.** The countermeasure that never worked was reading the output
more carefully.

### What the pattern says

Every one of these survived because **the claim was checked against a
report rather than against the tree**, and reports agree with each other
far more readily than they agree with a compiler. The three defences that
actually worked in this arc, in order of cost-effectiveness:

2. **Michelle using the product.** Found all three refuted claims above,

3. **Grepping the tree with a named search path**, and treating a
   "not found" as weaker than a "found".

#### Charcoal is the one item that is undecided rather than incomplete

Flagged separately because it is a different **kind** of debt from
everything else in this document, and it is the only place the arc's own
governing rule is being broken silently.

The facts: **Charcoal ships TrueType-only.** `Charcoal.ttf` carries no
`bdat`/`bloc` — there is no bitmap strike to extract, confirmed and
written up (`docs/charcoal-strike.md`; **written for** the corpus as
`charcoal-ships-scalable-only-no-bitmap-strike.md`, with
`hdmx-is-apples-own-per-ppem-advance-table.md` beside it, but **neither
has landed** — both sit on the parent's `claude/018-findings` branch, not
on its `main`, so a reader who looks for them in `data/findings/` will
not find them).

Closing it needs **one of two things, and neither has been chosen**:

- **(a) A TrueType rasteriser** — the honest fidelity answer, and the
  largest remaining text-fidelity gap in the product.
- **(b) An explicit decision to keep substituting Chicago, and to
  *declare* the substitution** — in the render, so a viewer can see that
  those glyphs are a stand-in, and in the fidelity instruments, so a
  measured width difference is attributed to the substitution rather than
  scored as a render defect.

**What happens today is neither.** We substitute Chicago, mis-measure
width against the machine, and **say nothing** — which is precisely the
*plausible wrong answer* this arc forbade everywhere else. Every other
gap in the product renders as a marked unknown; this one renders as
confident, wrong text. Two of slice 16's five "defects" were later traced
to exactly this (`d117c976`: the frame-through-label was *"Chicago
standing in for Charcoal"*), which is the cost already paid once for not
declaring it.

**This is Michelle's call and is not made here.** (b) is cheap and
immediately stops the mis-measurement; (a) is the real fix and is an arc.
The one option that is not available is the current one, because it is
the only place in the product where an unknown is being drawn as a known.

## Lessons this arc paid for, and where they belong

Three that are bigger than any row, in descending order of what they cost.

### 1. An instrument's default mode is where the defect hides — corpus

Eight instances in one arc, enumerated at
[The finding that changes the shape](#and-it-is-the-eighth-instance-of-one-pattern).
**This has enough instances to be a corpus finding rather than a docs
note**, and it generalises well past this repository. Suggested shape:
*an instrument whose default configuration is the defect's blind spot
reads green forever, and reading its output more carefully never recovers
the signal — only a second, differently-shaped observer does.*

### 2. A durable record is a file, not a list — and the rule has two levels

The arc committed `6fe8e213`, *"an agent's report is not a durable
artifact."* Task #35 shows the same rule failing one level up: **a plan
is the durable record and a task list is not.** A slice tracked only in
an ephemeral list is invisible to an audit derived from the plan, and the
audit will confidently report it does not exist. The disposition rule
should read: *work that is real gets a row in the durable document at the
moment it is claimed complete, not at the moment someone writes the
retrospective.*

`c4c70fa5` is this rule being applied correctly under pressure — five
sub-agent reports banked into a file because the context holding them was
about to compact.

<a name="two-merge-lessons-this-arc-paid-for-twice"></a>
### 3. Keep-both merges have now damaged this repo twice, in two languages

- **Slice 16's ledger entry** — newer heading kept, older body dropped.
  Caught by a reader, restored. *"A heading is not the entry."*
- **`tools/ext-bake-gate` / `tools/image-provenance`** — two lanes made
  the same change on divergent bases; the keep-both produced **six
  duplicate Python function definitions that still parsed as valid
  Python.** Caught only by a duplicate-`def` check, aborted, re-merged
  whole-file.

The existing memory *"keep-both merges truncate"* covers the C case,
where `build-guests` catches it via brace depth. **Neither of these two
would have been caught that way**: prose has no brace depth, and Python's
last definition silently wins. The generalised rule: **after any
keep-both resolution, verify the artifact's own integrity in its own
terms** — duplicate definitions for code, heading-has-a-body for prose —
because the languages that fail loudest are the ones already covered.
